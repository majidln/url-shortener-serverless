# Step 3 Guide — Nobody Told Us It Broke

A coaching guide, not a code drop. It names what to build and why; you write the
YAML.

**Goal (from [PLANNING.md](PLANNING.md)):** a bad deploy broke redirects and you
found out by clicking a link yourself. Add observability and safe deploys so the
system tells you first — and rolls a bad deploy back on its own.

**Exit:** three proofs (§6).

*A few $/month — the first thing that bills at rest. Still fine to leave running.*

---

## 1. Working directory

Same as before: one evolving stack in `url-shortener/`, steps marked by tags.
This is a `template.yaml` change plus a small canary script. The Go handlers
already emit JSON logs (`slog`, since Step 1) — Step 3 doesn't touch them.

---

## 2. The one lesson — alarm on the symptom, not the implementation

You'll be tempted to alarm on the redirect Lambda's `Errors` metric. It's wrong
twice.

**It's blind to the failure that matters.** A miss returns `404` cleanly; a
`GetItem` failure returns `500` cleanly — both are `return resp, nil`, so Lambda
records a *successful* invocation either way. Point `URL_TABLE_NAME` at a table
that doesn't exist and every redirect 500s while `AWS/Lambda Errors` sits flat at
zero.

**It's bound to the wrong thing.** `FunctionName=url-redirect` stops meaning
"redirects work" the moment Step 4 or 5 puts a cache or CloudFront in front and
traffic stops flowing through that exact function. The alarm goes quiet — not
because it's healthy, because its metric is dead.

So **page on the front door** — right now the HTTP API's `5xx`. Keep Lambda and
DynamoDB metrics on the *dashboard*: they're for diagnosis after the page, not
for paging.

## 3. What to add

**SNS topic + subscribers.** One `AWS::SNS::Topic` is the fan-out point — every
alarm's `AlarmActions` targets this, never a person directly, so you can add or
swap delivery without touching an alarm. Two subscribers:

- **Slack, via AWS Chatbot** (`AWS::Chatbot::SlackChannelConfiguration`) — the
  primary. The whole channel sees the alarm, threaded, no inbox rot. One-time
  manual step first: authorize the Slack workspace in the AWS Chatbot console
  (OAuth — can't be done in CloudFormation). After that the template just
  references `SlackWorkspaceId` + `SlackChannelId`, and Chatbot needs a small IAM
  role (`CloudWatch` read is enough for alarm messages).
- **Backup admin email** (`AWS::SNS::Subscription`, `Protocol: email`) — for when
  Slack is down or someone's not in it. Confirmation mail must be clicked or it
  delivers nothing.

Parameterize `SlackWorkspaceId`, `SlackChannelId`, `NotificationEmail` and put
the values in `samconfig.toml`, same as Step 2's domain — nothing hardcoded.
(Severity routing — a second `-critical` topic to PagerDuty/SMS — is the next
rung if the alarm count grows; one topic is right for now.)

**The paging alarm.** On `AWS/ApiGateway`, dimension `ApiId`, the `5xx` metric —
**as a fraction of `Count`, not a raw count**, and floored so one failed request
in a quiet hour can't page (metric-math expression gated on `Count`, or a
composite alarm ANDing "5xx rate high" with "traffic above X"). Set
`TreatMissingData` explicitly. Give it an explicit `AlarmName` — CodeDeploy
references it by name in §"safe deploys", and an autogenerated name can silently
change on a template edit. Make it sensitive enough that 10% of traffic failing
trips it inside five minutes.

**Log groups with retention.** Declare `AWS::Logs::LogGroup` for each function,
name `/aws/lambda/${ThatFunction}`, `RetentionInDays` set. Left implicit, Lambda
creates them as *never expire* and they outlive `sam delete`. Gotcha: if a
function has already run its log group exists, and CloudFormation won't create a
duplicate — delete the existing group first or the deploy fails.

**Dashboard.** One `AWS::CloudWatch::Dashboard` JSON body: API Gateway (`Count`,
`4xx`, `5xx`, `Latency`), each Lambda (`Invocations`, `Errors`, `Duration`,
`Throttles`, `ConcurrentExecutions`), DynamoDB (`ConsumedReadCapacityUnits`,
`ThrottledRequests`, `SuccessfulRequestLatency`).

**Synthetic canary.** `AWS::Synthetics::Canary` — no SAM shorthand, raw
resource. A tiny Node/Python script that does `GET https://<domain>/<known-code>`
every 5 minutes and asserts `302` + a `Location` header. Needs an IAM role and an
S3 bucket for artifacts. ~$1/month, and not optional: at 3am with no organic
traffic the paging alarm has nothing to evaluate, and **CodeDeploy's
auto-rollback depends on that alarm being able to reach a state during the
five-minute bake.** The canary is the heartbeat.

**Safe deploys.** On the redirect function: `AutoPublishAlias: live` and

```
DeploymentPreference:
  Type: Canary10Percent5Minutes
  Alarms:
    - !Ref RedirectHealthAlarm
```

SAM creates the CodeDeploy app, the alias, and the traffic shift. A new version
goes to 10% of traffic; CodeDeploy watches the alarm for five minutes; if it
trips, it shifts back to the old version on its own. The serverless stand-in for
testing in a copy of prod.

## 4. Traps

- **Rate, not count** — `5xx / Count`, floored. Covered above; it's the one
  people get wrong.
- **`TreatMissingData`** — set it on every alarm. `notBreaching` is usually
  right; with the canary running you shouldn't see gaps anyway.
- **Log retention** — the never-expire default is a slow bill and an orphan
  waiting to happen. Every log group gets a retention.
- **Canary IAM** — managed policy `CloudWatchSyntheticsExecutionRolePolicy`, plus
  `s3:PutObject` to its bucket and `logs:` for its own logs.
- **Don't hardcode "redirects flow through this function."** Step 5 moves the
  symptom to CloudFront's metrics; the alarm is meant to be re-pointed at the new
  front door, not rewritten.

---

## 5. Order

1. Authorize the Slack workspace in the AWS Chatbot console (one-time). Then SNS
   topic + Chatbot Slack config + backup email subscription; confirm the email.
2. Log groups (delete any pre-existing ones first), retention set.
3. The `5xx`-rate alarm → SNS. Deploy.
4. Canary script + `AWS::Synthetics::Canary` + role/bucket. Deploy, watch it go
   green.
5. `AutoPublishAlias` + `DeploymentPreference` on the redirect function, alarm
   attached. Deploy.
6. Dashboard.
7. Run the three proofs (§6).
8. `git tag step-3-complete`.

---

## 6. Definition of done — three proofs

1. **The pipe works.**
   `aws cloudwatch set-alarm-state --alarm-name <name> --state-value ALARM
   --state-reason test` → the email lands. Set it back to `OK`.
2. **Real break, detected and recovered.** Point the redirect function's
   `URL_TABLE_NAME` at a table that doesn't exist (or pull its
   `DynamoDBReadPolicy`), deploy. Within minutes: canary fails → `5xx` rate
   climbs → alarm fires → email. Revert, deploy, watch it return to OK.
3. **Bad deploy, rolled back automatically.** Ship a redirect handler that always
   500s (or `panic()`s on init). Watch CodeDeploy move 10% of traffic, the alarm
   trip inside the five-minute window, and the alias shift back to the previous
   version with no action from you. Confirm `curl https://<domain>/<code>` is a
   `302` again.

Record in RESULTS.md: alarm→email latency, and how long proof 3's rollback took
end to end.
